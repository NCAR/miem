# MIEM Scientific Review: Atmospheric Scientist Evaluation

## Executive Summary

MIEM v1 is a well-structured software scaffolding for an emissions processing module. The C++/C/Fortran architecture is clean and the design principles (host-model independence, configuration-driven operation, the `EmissionSource` abstraction) are sound. However, from a scientific correctness and atmospheric chemistry standpoint, the implementation has significant gaps and several scientifically incorrect or incomplete behaviors that would need to be addressed before MIEM could be used in a production atmospheric model. These range from a non-functional temporal interpolation engine (it only ever brackets from the same static file), to missing diurnal cycle support, to a unit handling system that relies entirely on user-supplied scalars with no self-checking, to an incomplete VOC speciation model. The structure is right; the science needs to be filled in.

## 1. Emissions Data Handling and CES Reader

### Scientific Assessment: Structurally Sound, But Missing Metadata Validation

The `CESReader` (`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/ces_reader.cpp`) correctly detects file format via the `miem_version` global attribute (line 52), discovers species by variable prefix (`emi_*`, line 88-100), and reads 1-D or 2-D (Time, nCells) arrays via NetCDF-C calls.

**Problem 1: Time coordinate is read but not interpreted (lines 128-140 in ces_reader.cpp).**
`GetTimeValues()` reads the raw double values from the `Time` variable but does not read the `units` attribute of that variable (e.g., `"days since 2000-01-01"`, `"hours since 1970-01-01 00:00:00"`). The raw numbers are passed directly to the temporal interpolator as seconds (the bracket search in `source_offline.cpp` lines 57-58 compares `times[t] <= time_current`). If the file stores time in days since a reference epoch and the host model passes time in seconds since a different epoch, the bracket search will silently fail, producing wrong or zero emissions. This is a fundamental CF-Conventions violation. Real-world files (CEDS, EDGAR, GFED, FINN) all use `CF:units` and `calendar` attributes on their time coordinate, and a production reader must parse these.

**Problem 2: Fill value and missing value handling is absent.**
No code reads `_FillValue`, `missing_value`, or `valid_range` from emission variables. For datasets like GFED where ocean cells carry fill values, raw flux data will contain large negative or sentinel values that will pass through all layers to the host model as unphysical emissions.

**Problem 3: CES compliance detection is fragile.**
The test is simply whether `miem_version` exists as a global attribute (line 52-53). The `validate_ces.py` script (line 25) confirms this is the only required marker. A file that happens to have any `miem_version` attribute would be treated as fully CES-compliant, bypassing all descriptor overrides, even if it has non-standard dimension names. The compliance flag should be a multi-criteria check (required dimensions, required variable naming convention, required units attribute).

**Problem 4: No support for 3-D emissions in the reader.**
The `ReadFlux` method handles only 1-D (`nCells`) and 2-D (`Time, nCells`) variables (lines 186-202). GFED and some CEDS sectors provide emissions on a 3-D grid `(Time, Level, nCells)` for elevated sources (e.g., stack heights, aircraft). The reader silently skips any variable with ndims != 1 or 2 without raising an error.

## 2. Temporal Interpolation

### Scientific Assessment: Architecturally Correct, But Bracket Loading is Broken for Real Use

The `TemporalInterpolator` class (`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/temporal_interpolator.cpp`) itself is mathematically correct: linear interpolation (lines 55-68), nearest neighbor (lines 48-52), and constant modes are all implemented cleanly with proper alpha clamping and degenerate-case handling.

**Critical Problem: The bracket is only ever loaded once per file (source_offline.cpp lines 38-88), and `ResolveFilePath()` always returns the same static path (line 32-36).**

The comment in `ResolveFilePath()` at line 33-35 explicitly acknowledges this: "For v1, return the file pattern directly. Future: expand `{YYYY}{MM}{DD}` tokens based on time." This means:

- Monthly emissions (CEDS, EDGAR): MIEM will read January data and use it for the entire simulation year. Month transitions will never load new data.
- Daily fire emissions (FINN, GFED daily): Same — the first day's file is never replaced.
- The `CoversTime()` check in `Update()` (line 94) will return false once the model advances past the first bracket, triggering `LoadBrackets()` again on the same file. On a file with 2 time steps, the bracket indices will saturate at `{n_times-2, n_times-1}` (lines 65-68 in source_offline.cpp) and hold constant for all subsequent model time steps. Emissions will be frozen.

**Missing: Diurnal cycle support.**
Standard anthropogenic emissions inventories (CEDS, EDGAR) are monthly. Applying a diurnal profile (typically a normalized 24-hour cycle per sector from Olivier et al. or CAMS temporal factors) is a standard pre-processing step. MIEM has no mechanism for this. HEMCO and GOCART-2G both support diurnal multiplier fields that are applied on top of the monthly base emissions. MIEM's `TemporalInterpolator` could support this if an additional multiplicative diurnal profile layer were added.

**Missing: Climatological cycle ("cycling") mode.**
Monthly climatological inventories must wrap around: December (time step 12) and January (time step 1) must be bracketed at year-end. The current bracket search will simply freeze at the last time step when `time_current > times[n_times - 1]` (lines 65-68 in source_offline.cpp). There is no modular arithmetic or wrap-around for climatological cycling.

**Missing: Nearest-neighbor for monthly data.**
For monthly average datasets where the correct semantics is "use January values for all of January," nearest-neighbor mode is appropriate. However, the midpoint test in `kNearest` (line 49: `double mid = 0.5 * (time_left_ + time_right_)`) computes the arithmetic mean of two timestamps in whatever time unit the file uses. For monthly data this is numerically correct only if the two timestamps are the midpoints of their respective months. Most inventories store timestamps at the start of the month (day 1, hour 0), so the midpoint would be the 15th of month M, meaning data transitions in the middle of the month rather than at the start. This is scientifically acceptable but should be documented.

## 3. Species Mapping and Resolution

### Scientific Assessment: Design is Good, Implementation Has Important Limitations

The `SpeciesMap` class (`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/species_map.cpp`) correctly implements the N:M fan-out pattern (one inventory species maps to multiple mechanism species with individual scaling factors). The `Apply()` method at lines 84-120 correctly accumulates across all mappings, enabling both 1:1 passthrough and speciation.

**Problem 1: The scaling factor warning is scientifically inadequate (lines 52-59 in species_map.cpp).**
The warning `"scaling factors for inventory species 'X' sum to N (>1.0) — mass is being amplified"` uses a greater-than-1.0 threshold. However, it emits no warning when the sum is less than 1.0 (mass destruction). For VOC speciation, it is common and scientifically legitimate for scaling factors to sum to less than 1.0 (the rest goes to unspeciated NMVOC that the mechanism does not track). But in other contexts, a sum less than 1.0 is a configuration error. There should be a way to declare whether a mapping is "mass-conserving" (must sum to 1.0) or "fraction-based" (allowed to not sum to 1.0). The example species map (`configs/example_species_map.yaml`) maps NMVOC to three mechanism species with factors 0.3+0.2+0.15=0.65, silently discarding 35% of NMVOC mass with no warning.

**Problem 2: Species name matching is case-sensitive exact-match only.**
`ResolveHostIndices()` (`emissions_module.cpp` lines 45-62) uses `std::map<std::string, int>` with exact string matching. Real-world inventories and chemical mechanisms use inconsistent naming: `NO`, `no`, `No`, `NOx`, `nox`, `NOX`, `NO_x`. HEMCO handles this with case-insensitive matching and an alias system. MIEM will silently return `-1` (not found) for any case mismatch.

**Problem 3: No molar mass conversion in the species mapping layer.**
The `scaling_factor` in `SpeciesMapping` is documented as "mass-based" (header, line 13 of species_map.hpp). But many inventories report NOx as NO2-equivalent mass while models track NO and NO2 separately in terms of molecular mass. Converting NOx (as NO2-equivalent, molecular weight 46 g/mol) to NO (molecular weight 30 g/mol) requires multiplying by 30/46 = 0.652, not 0.9 and 0.1. The example config uses 0.9/0.1 for NO/NO2 split of NOx without clarifying whether this is a mass-fraction split or a molar-fraction split, and there is no facility to declare or enforce the distinction.

**Problem 4: Aggregation across sources uses simple addition without any mass-balance check (emissions_module.cpp lines 77-93).**
When the same mechanism species appears in both the anthropogenic and fire emission sources (e.g., `CO` from CAMS and `CO` from FINN), their fluxes are added element-wise at line 90. This is scientifically correct. However, if the two sources have different `n_cells` (e.g., the file was generated for a different grid), the inner loop at line 89 will silently use the wrong values because both are indexed by `n_cells_` without validation of the source's actual cell count against `n_cells_`.

## 4. Spatial Considerations

### Scientific Assessment: Deliberately Grid-Independent, But Fragile

The flat `nCells` convention is consistent with the MPAS/MPAS-A unstructured mesh world, where columns are the fundamental spatial unit. For structured grid models (CAM-SIMA, WRF), columns are obtained by linearizing the 2-D lat-lon grid. This is a valid design choice and matches what MICM does.

**Problem 1: Cell count mismatch between file and host is not validated.**
`OfflineEmissionSource::Update()` receives `n_cells` from `EmissionsModule::Run()` (emissions_module.cpp line 81), but `LoadBrackets()` reads the cell count from the file (`reader_.NumCells()`). If the file was preprocessed for 40,962 cells but the model has 40,960 cells (a common regridding edge case), the species mapping `Apply()` call at line 79 uses `n_cells` (reader's count) while the outer aggregation loop at line 89 uses `n_cells_` (module's count). This will either corrupt memory or silently produce incorrect results.

**Problem 2: No coordinate metadata is read or stored.**
The CES reader does not read latitude/longitude coordinate variables. This means MIEM cannot validate that a file is spatially consistent with the host model's domain (e.g., a global file vs. a regional domain file). All spatial matching is left entirely to the upstream preprocessing (UPTEMPO or equivalent).

## 5. Unit Handling

### Scientific Assessment: Dangerously Simplistic

The unit system in MIEM reduces to a single scalar multiplier: `DatasetDescriptor::unit_conversion_factor` (a `Real`, defaulting to 1.0). This is applied uniformly to all species in the file (ces_reader.cpp lines 204-208).

**Problem 1: Unit conversions are not species-aware.**
Different species in the same file may have different units (e.g., some inventories report aerosol precursors in `μg m-2 s-1` and gas-phase species in `kg m-2 s-1`). A single scalar cannot handle mixed-unit files. HEMCO applies per-species unit conversions; GOCART-2G embeds unit attributes on each variable. MIEM reads `var.units` attributes in `validate_ces.py` (line 54) but the C++ reader never reads or uses them.

**Problem 2: The example descriptor has a likely incorrect unit conversion factor.**
In `test/unit/test_config.cpp` line 42 and `configs/example_descriptor.yaml` line 3:
```
flux_units: "molecules/cm2/s"
unit_conversion_factor: 1.66054e-21
```
Converting `molecules cm-2 s-1` to `kg m-2 s-1` requires: multiply by molecular mass (g/mol), divide by Avogadro's number (6.022e23), multiply by 1e-3 (g to kg), multiply by 1e4 (cm-2 to m-2). For CO (molecular mass 28 g/mol): `28 / 6.022e23 / 1e3 * 1e4 = 4.65e-22 kg per molecule per m-2`. The factor `1.66054e-21` corresponds to `1 / (6.022e23) * 1e4 / 1e3 = 1 amu * m2/cm2 * kg/g` — this is `1 amu = 1.66054e-27 kg` converted, but it equals 1/Avogadro in kg, which would be correct only for a species with molecular weight of 1 g/mol (hydrogen atoms). For CO the factor is off by a factor of 28, and for NOx (as NO2) by a factor of 46. A correct implementation must either read the molecular weight from a configuration or from the file's attributes.

**Problem 3: The `flux_units` string field in `DatasetDescriptor` is never parsed or validated by the C++ code.** It is stored as a string (dataset_descriptor.hpp line 14) but no code ever reads it to derive the conversion factor. It is documentation only. A user who provides `flux_units: "molecules/cm2/s"` but `unit_conversion_factor: 1.0` will get emissions that are 21 orders of magnitude too large, with no error.

MIEM v1 cannot handle any of these without significant extensions. The most critical gaps:

## 7. GOCART-2G Comparison

GOCART-2G (as implemented in GFDL FV3/GEOS) provides the most direct architectural comparison. Key lessons from GOCART-2G that MIEM has not yet absorbed:

**What GOCART-2G does that MIEM lacks:**

1. **Climatological cycling with calendar-aware time interpolation.** GOCART-2G uses a `CF_Time` module that parses NetCDF `time:units` and `time:calendar` attributes, converts to a common internal epoch, and supports annual cycling for monthly climatologies. MIEM has no calendar awareness.

2. **Per-species molecular weight table.** GOCART-2G maintains an internal table of molecular weights for all tracked species and uses this to convert between molar and mass emission rates. MIEM's `scaling_factor` is a single real number with no unit annotation.

3. **Sector aggregation is explicit in configuration.** GOCART-2G configuration files explicitly list which sectors (ENE, IND, TRA, etc.) contribute to each mechanism species, with individual sector scaling factors (for sensitivity studies or policy scenarios). MIEM has `SourceConfig::type` (anthropogenic, fire, biogenic) but no sector-level decomposition.

4. **Dynamic scaling factors for sensitivity and scenario runs.** GOCART-2G supports `scaling_factor` fields that can be time-varying or scenario-specific multipliers applied at the sector level. This is essential for emissions sensitivity experiments. MIEM's `scaling_factor` is a compile-time constant per mapping entry.

5. **Online dust and sea-salt emission parameterizations.** These are computed from host-model wind speed, soil properties, and sea surface state at every time step. MIEM's `EmissionSource` base class defines `Update(double time_current, int n_cells, ...)` with no mechanism to pass host-model meteorological state. Online sources cannot be implemented within the current interface.

6. **Regridding as an integrated capability.** GOCART-2G calls ESMF regridding internally for most sources. MIEM deliberately defers regridding to UPTEMPO. This is a defensible design choice for a MUSICA module, but it means MIEM is unusable without an upstream preprocessing step that does not yet exist for all target grids.

**Where MIEM's design is superior to or competitive with GOCART-2G:**

1. The three-layer C++/C/Fortran API is cleaner than GOCART-2G's Fortran-only interface and enables use from Python or other languages.
2. The `DatasetDescriptor` pattern for non-standard files is more explicit and maintainable than GOCART-2G's internal format-specific readers.
3. The `EmissionSource` abstract base class is a cleaner extension point than GOCART-2G's procedural dispatch.

# MIEM MUSICA Ecosystem Compatibility Evaluation

## Executive Summary

MIEM is a well-structured v1 implementation that follows the MUSICA three-layer architecture pattern faithfully. The C++ core is clean, the C API error handling closely mirrors MICM's `HandleErrors` template, and the Fortran `iso_c_binding` layer is complete enough for a host model to call. However, there are specific gaps that must be addressed before MIEM can be used in a production CAM-SIMA/CCPP integration. The most critical are: a `HandleErrors` catch ordering bug that silently eats MIEM's own typed exceptions, the fixed-`double` C API that breaks when `MIEM_USE_DOUBLE` is off, and a Fortran layer that is not yet shaped for CCPP metadata compliance. The dependency strategy has one significant deviation from MUSICA convention: yaml-cpp is fetched unconditionally rather than being optional for downstream consumers.

## 1. Three-Layer Architecture and MICM Comparison

### Overall Conformance

The pattern is correct: C++ classes in `include/miem/` and `src/`, opaque-pointer `extern "C"` functions in `src/c_interface/`, and Fortran derived types with `iso_c_binding` interfaces in `fortran/`. This mirrors MICM's layout (`include/micm/`, `src/micm/`, `src/micm/util/error.hpp`, `fortran/`).

### HandleErrors Template

`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/c_interface/error_handling.hpp`, lines 39-52.

The template exists and is used consistently on every C API function. The structure is correct. However there is a catch-ordering defect at line 44:

```cpp
} catch (const MIEMError& e) {
    // Already a C error struct — shouldn't happen but handle gracefully
    if (error) *error = e;
```

`MIEMError` here refers to the C struct (`struct MIEMError { int code; char category[64]; char message[256]; }`) defined earlier in the same header at line 9. But the C++ exception hierarchy defined in `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/include/miem/util/error.hpp` also uses the name `miem::MIEMError` (a `std::runtime_error` subclass). Inside `namespace miem::c_api`, the unqualified `MIEMError` resolves to the C struct in the outer `extern "C"` block, not the C++ exception type. This means `ConfigError`, `IOError`, `SpeciesError`, and `ValidationError` — which all inherit from `miem::MIEMError` — will fall through to the `std::exception` handler at line 47 and lose their category string. Their messages survive, but the `category` field will always read `"Exception"` instead of `"Configuration"`, `"IO"`, etc. The fix is to catch `const miem::MIEMError& e` (the C++ type) explicitly before `std::exception`. In MICM this ambiguity does not arise because MICM uses a separate `Error` struct type rather than reusing the C boundary name.

### C API Surface

`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/c_interface/miem_c_interface.cpp`

`MIEMRun` at line 65 takes `const double*` for `air_density` and `layer_thickness` regardless of the `MIEM_USE_DOUBLE` compile flag. When the library is built with `MIEM_USE_DOUBLE=OFF`, `Real = float`, and the internal conversion at line 71-72 (`std::vector<Real> rho(air_density, air_density + n_atm_elements)`) silently truncates the caller's doubles to floats. The C API should use `const Real*` (exposed as a `#ifdef`-guarded typedef in a public header) or document that the C API is always `double`. MICM takes the latter approach and documents it explicitly.

The `emis_state_c_interface.cpp` data-pointer functions `MIEMGetSurfaceFlux` and `MIEMGetTendency` at lines 9-16 return `double*` unconditionally for the same reason.

There is no C header (`miem.h`) declaring these functions. Every caller — including the Fortran module — re-declares the prototypes manually. MICM ships `include/micm/micm.h`. MIEM needs an equivalent public C header so that host models written in C, Python (via ctypes/cffi), or Julia can consume the API without transcribing the signatures.

### Fortran iso_c_binding Layer

`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/fortran/miem.F90` and `emis_state.F90`

The Fortran `miem_t` type correctly wraps an opaque `c_ptr`, declares `init`/`run`/`finalize` as type-bound procedures, and uses `miem_util_mod::error_t` (a `bind(C)` struct matching `MIEMError`). These are the right structural choices.

Three specific issues in the Fortran layer:

**Issue F1 — `CreateMIEM` error argument (`miem.F90` line 30).**
The interface declares `error` as `type(c_ptr), value :: error`. This passes a pointer-to-pointer, which is wrong when the Fortran caller writes `c_loc(error)` at line 100 — that produces a C pointer to the `error_t` struct, which is what the C function expects (`MIEMError*`). Actually the `c_loc(error)` usage is correct at the call site, but the interface declaration says `type(c_ptr), value` meaning it expects a `c_ptr` by value, not a pointer to an error struct. The correct declaration should be `type(MIEMError_t), intent(inout)` with `bind(C)` semantics, or equivalently pass `c_loc(error)` as `type(c_ptr), value` at the interface level. The current code is inconsistent: `c_loc(error)` produces a raw C address, then it is passed where the interface says `type(c_ptr), value` — this will compile but may misbehave on strict ABI targets. MICM's Fortran bindings pass error structs by reference using explicit `type(c_ptr)` at the interface and `c_loc()` at the call site, which is what MIEM does at line 100. The interface prototype at line 30 needs to declare `error` with `intent(in)` removed and typed consistently.

**Issue F2 — Array memory layout in `emis_state.F90` lines 82-90.**
The C `surface_flux` layout is `[species * n_cells + cell]` (species-major, row = species). The Fortran `c_f_pointer` reinterpretation at line 82 uses shape `[this%n_cells, this%n_species]`. Since Fortran is column-major, `surface_flux(ic, isp)` in Fortran maps to offset `(isp-1)*n_cells + (ic-1)` in C — which is correct. The comment at line 79 says "(n_species, n_cells) — species-major in C, becomes (n_cells, n_species)" which correctly describes the transposition. This is fine, but it must be documented as a deliberate convention because it will surprise CAM-SIMA developers who expect `(species, cell)` Fortran ordering. Similarly, `tendency` at lines 86-90 uses shape `[n_cells, n_vert_levels, n_species]` matching the C layout `[species * n_vert_levels * n_cells + level * n_cells + cell]`. The mapping is correct but the innermost-fast dimension difference needs explicit documentation in the interop header.

**Issue F3 — `miem_resolve_host_indices` string passing (`miem.F90` lines 136-150).**
The construction of `c_names` as `type(c_ptr), allocatable, target :: c_names(:)` and `c_strings` as `character(len=64, kind=c_char)` is a reasonable approach, but the hardcoded length of 64 characters per species name at line 137 is a silent truncation hazard. Species names longer than 63 characters (unlikely in practice, but possible in custom mechanisms) would be silently truncated with no warning. MICM uses a parameter constant for its maximum name length; MIEM should do the same and emit a diagnostic if truncation would occur.

## 2. CCPP/CAM-SIMA Integration Readiness

The three lifecycle phases are structurally present:
- Init: `miem_t%init(config_path, n_cells, n_vert_levels, error)` — `miem.F90` line 89
- Run: `miem_t%run(time_current, dt, air_density, layer_thickness, state, error)` — line 105
- Finalize: `miem_t%finalize(error)` — line 170

This is the right shape. However CCPP physics schemes require specific conventions that MIEM does not yet satisfy:

**CCPP metadata.** CCPP schemes must have a companion `.meta` file (or DDT metadata) declaring every argument with `standard_name`, `units`, `dimensions`, and `intent`. MIEM has none of this. Before wrapping as a CCPP scheme, each argument to the run subroutine needs a `standard_name` from the CCPP Standard Names Library — for example, `air_density` would be `air_density_of_dry_air_and_water_vapor` and `layer_thickness` would need a CCPP-recognized pressure or thickness name.

**CCPP subroutine naming.** CCPP requires the scheme name to appear as a prefix in the subroutine names: e.g., `miem_init`, `miem_run`, `miem_finalize`. The current names (`miem_t%init`, `miem_t%run`, `miem_t%finalize`) are type-bound procedures on `miem_t`. CCPP cannot call type-bound procedures directly; it needs standalone subroutines with the correct naming convention. A thin CCPP wrapper module that delegates to the `miem_t` methods would be the right approach — this wrapper does not yet exist.

**Host model constituent array pattern.** CAM-SIMA provides constituents as a 3D array `(ncol, pver, pcnst)` through its `cam_constituents` infrastructure. The current MIEM interface takes separate `air_density` and `layer_thickness` arrays and returns an `emis_state_t` that the host must then scatter into its constituent array using `emis_to_chem_idx`. This is workable but requires a non-trivial coupling layer in the host. Consider whether MIEM should accept (or optionally accept) the full constituent tendency array as an inout argument and write directly to it — more complex but reduces coupling code in the host model.

**`dt` parameter.** The `miem_run` interface accepts a `dt` timestep argument (`miem.F90` line 109) that is passed to `MIEMRun` but the C++ `EmissionsModule::Run` at `emissions_module.cpp` line 64 receives `dt` without using it in any computation. The `FluxConverter::Convert` call at line 97 does not use `dt`. This is a placeholder that may confuse integrators who assume `dt` is applied. Either use it (some emission schemes scale by `dt` to produce increments) or remove it from the interface with a comment explaining the design decision.

## 3. EmisState and Data Exchange

### Pointer Pattern vs. MICM

MICM's `State` and `RateConstants` expose data via `.data()` on internal `std::vector` members, and the Fortran layer uses `c_f_pointer` to wrap those raw pointers into Fortran array pointers. MIEM follows this exact pattern:

- `EmisState::SurfaceFluxData()` / `TendencyData()` / `EmisToChemIdxData()` — `emis_state.hpp` lines 38-45
- `MIEMGetSurfaceFlux` / `MIEMGetTendency` / `MIEMGetEmisToChemIdx` in `emis_state_c_interface.cpp`
- `c_f_pointer` calls in `emis_state.F90` lines 82-97

This is structurally correct and consistent with MICM.

### Ownership Semantics

`MIEMRun` allocates a new `EmisState` on the heap (`new EmisState(...)` at `miem_c_interface.cpp` line 73) and returns a `void*`. The caller is responsible for calling `DeleteMIEMState`. In the Fortran layer, `emis_state_t%delete` calls `DeleteMIEMState_c`, but there is no destructor or `FINAL` procedure on `emis_state_t`. If a Fortran host goes out of scope without calling `state%delete(error)`, the `EmisState` leaks. MICM uses `FINAL` procedures on its Fortran wrapper types. MIEM should add `FINAL :: emis_state_destructor` to `emis_state_t` (`emis_state.F90` line 15).

### State Returned vs. State Accumulated

`MIEMRun` returns a freshly allocated `EmisState` on every call. This means every time step requires a heap allocation followed by a deallocation after the host reads the data. For high-frequency calls in a large model, this adds allocation pressure. MICM avoids this by mutating state in-place. Consider an in-place variant: `MIEMRunInPlace(void* miem, void* state, ...)` where the host pre-allocates one `EmisState` and MIEM writes into it. The current allocation-per-call approach is acceptable for v1 but should be noted as a performance consideration.

### Array Layout Documentation

The layout comment in `emis_state.hpp` lines 16-21 (`flux[species_idx * n_cells + cell_idx]`) is critical information for integrators. It should be replicated in the C API header (once that exists) and in the Fortran module as a comment on `surface_flux` and `tendency`. The Fortran array pointer shapes (`[n_cells, n_species]` and `[n_cells, n_vert_levels, n_species]`) established in `emis_state.F90` lines 82-90 are the authoritative access pattern for Fortran callers and need more prominent documentation.

## 4. Species Discovery: QuerySpecies and ResolveHostIndices

### Design Alignment with MICM

MICM's constituent registration pattern uses `micm::SolverParameters::species` and the solver builder to enumerate known species before construction, with the host passing its own list for index mapping. MIEM implements a parallel two-phase protocol:

1. `EmissionsModule::QuerySpecies(config_path)` — static, reads YAML and opens source objects to extract mechanism species. Call this before constructing.
2. `EmissionsModule::ResolveHostIndices(host_species, indices)` — instance method, maps emission species to host chemistry indices.

This is structurally correct. However there are two issues:

**Issue S1 — Double config parsing.** `QuerySpecies` at `emissions_module.cpp` line 14 calls `MIEMConfig::FromYAML(config_path)` and constructs an `OfflineEmissionSource` per source just to call `QuerySpecies()` on it. Then the constructor at line 28 calls `MIEMConfig::FromYAML` again and constructs `OfflineEmissionSource` objects a second time. For sources that open NetCDF files during construction (they do — `OfflineEmissionSource` loads the species map from YAML in its constructor at `source_offline.cpp` line 15), this doubles the I/O cost of initialization. MICM avoids this by separating configuration parsing from object construction. Consider a `MIEMConfig` + `static QuerySpecies(const MIEMConfig&)` overload, or caching parsed config.

**Issue S2 — `ResolveHostIndices` output length.** The method resizes `indices` to `aggregated_species_.size()` (`emissions_module.cpp` line 48), meaning the output is indexed by emission species, not by host species. The host must therefore iterate over emission species and use `indices[i]` to find where to scatter species `i` into the host's chemistry array. The docstring in `emissions_module.hpp` line 24 says "maps each emission species to its host index" which is correct, but this is the opposite of MICM's constituent index convention (MICM maps host constituent index to mechanism species index). This is a valid design choice but should be called out explicitly in documentation, as a CAM-SIMA developer will initially assume the MICM convention.

**Issue S3 — Index base mismatch.** `ResolveHostIndices` sets `indices[i] = -1` for not-found species (`emissions_module.cpp` line 48). In the Fortran layer, the `emis_to_chem_idx` pointer is `integer(c_int)` and a value of -1 from C maps correctly to -1 in Fortran. However Fortran arrays are 1-based by default. A host developer reading `emis_to_chem_idx(i)` and using it as a Fortran index will need to add 1. This is a common source of off-by-one errors at language boundaries. MICM documents this convention explicitly and some versions provide a Fortran-specific +1 adjustment. MIEM should do the same.

## 5. YAML Configuration Compatibility

The YAML configuration approach is consistent with MUSICA philosophy — MusicBox, MICM's box model driver, and TUV-x all use YAML as the configuration format. The specific structure (`miem:` top-level key, `sources:` list, per-source `species_map:` reference) is clean and readable. The example configs in `configs/` demonstrate the intended pattern clearly.

**Issue C1 — yaml-cpp as a PUBLIC link dependency.** In `src/CMakeLists.txt` line 26-27, yaml-cpp is `PUBLIC`, which means any downstream CMake project that does `find_package(MIEM)` or uses the installed `musica::miem` target will automatically have yaml-cpp as a transitive compile and link dependency. This is unnecessary: yaml-cpp is used only in MIEM's `.cpp` files and has no presence in any public header. It should be `PRIVATE`. MICM has the same consideration with its dependency management. Leaving it `PUBLIC` will cause yaml-cpp to contaminate the downstream build graph, potentially conflicting with the host model's own yaml-cpp version.

**Issue C2 — FetchContent for yaml-cpp is always ON.** `cmake/dependencies.cmake` line 4-12 always fetches yaml-cpp via FetchContent. For downstream users who already have yaml-cpp installed (e.g., MUSICA's monorepo, which manages yaml-cpp centrally), this causes a second copy to be built. The pattern should be `find_package(yaml-cpp QUIET)` first, and only `FetchContent_Declare` if not found. MICM uses this two-phase approach.

**Issue C3 — `MIEMConfig` exported in public headers.** `include/miem/config.hpp` exposes `MIEMConfig::FromYAML` in the public include path. This pulls `miem/temporal_interpolator.hpp` (for `InterpolationMode`) into the public API of `config.hpp`. Host models that only need the C API or Fortran bindings should not need to know about internal config types. The public umbrella header `include/miem/miem.hpp` exposes all internal headers including `config.hpp`, `ces_reader.hpp`, `dataset_descriptor.hpp`, etc. This is fine for C++ consumers but the header organization should distinguish the "user-facing" API (C++ core: `EmissionsModule`, `EmisState`) from the "internal plumbing" (config parsing, CES reader, species map, flux converter). MICM separates these via a `micm/micm.hpp` convenience header vs. individual subsystem headers.

# MIEM Architectural Review

## Executive Summary

MIEM is a well-structured scientific computing module with a clean three-layer design, good SOLID alignment for a v1 codebase, and thoughtful conventions inherited from the MICM pattern. The primary concerns are not with the overall architecture — which is sound — but with several specific design choices that will become pain points as the module grows: a hardwired concrete type inside `EmissionsModule`, several memory ownership hazards at the C/Fortran boundary, a `Real`-type mismatch at the C API, and a `CESReader` that conflates too many responsibilities. None of these are blockers; they are correctable with targeted, backward-compatible changes.

## 1. Overall Architecture: Three-Layer Design

**Verdict: Clean, with one abstraction leak at the C boundary.**

The layering is correctly ordered and the intent is sound:

```
miem::EmissionsModule / miem::EmissionSource
         |
src/c_interface/  (error_handling.hpp + two .cpp files)
         |
fortran/miem.F90 + emis_state.F90 + util.F90
```

Each layer adds a narrow, well-defined transformation: the C++ layer owns all memory and all logic; the C layer translates exceptions to error structs and object lifecycles to opaque `void*`; the Fortran layer wraps those pointers in derived types and re-exposes them with idiomatic Fortran procedure binding.

**Abstraction leak — `Real` vs `double` at the C boundary.**

`MIEMRun` in `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/c_interface/miem_c_interface.cpp` at line 65 declares `air_density` and `layer_thickness` as `const double*`, hard-coded regardless of the `MIEM_USE_DOUBLE` compile flag. The Fortran interface at `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/fortran/miem.F90` line 111 correctly uses `real(c_double)`, but the two `emis_state_c_interface.cpp` accessors `MIEMGetSurfaceFlux` and `MIEMGetTendency` return `double*` regardless of precision mode. When `MIEM_USE_DOUBLE=OFF`, the internal `EmisState` holds `float` data but the C API hands out `double*` — a type-punning error. The `types.hpp` `Real` alias exists precisely to abstract this, but it was not applied to the C boundary.

**Abstraction leak — `MIEMQuerySpeciesNames` buffer contract is undocumented.**

`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/c_interface/miem_c_interface.cpp` line 43 calls `strncpy(names[i], ..., 63)`. The magic constant 63 is not defined anywhere — no `MIEM_MAX_SPECIES_NAME_LEN` constant — so Fortran callers must allocate `character(len=64, kind=c_char)` and know to match this number. The Fortran module at line 137 does this correctly, but the contract is implicit rather than enforced.

## 2. Class Design and Separation of Concerns

**EmissionsModule: good orchestration, one tight coupling.**

`EmissionsModule` at `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/include/miem/emissions_module.hpp` manages a `vector<unique_ptr<EmissionSource>>` which is correct OCP design. However, the constructor at `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/emissions_module.cpp` lines 35-39 directly instantiates `OfflineEmissionSource`. This couples the module orchestrator to a concrete subclass, bypassing the `EmissionSource` interface entirely. When a second source type (say, `OnlineBiogenicSource`) is added, `EmissionsModule.cpp` must be edited to add another `if (src_config.type == "biogenic")` branch. This is a direct OCP violation.

The fix is a factory: a `SourceFactory::Create(const SourceConfig&)` free function (or static method) that maps `src_config.type` to concrete subclass construction, keeping `EmissionsModule` free of concrete type names.

**`EmissionSource` interface: mostly right, one design smell.**

`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/include/miem/source.hpp` defines a clean abstract base. The `Init(config_path)` method at line 18, however, was designed as an alternative construction path but `OfflineEmissionSource::Init` at `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/source_offline.cpp` line 24 is a no-op stub with the comment "Already initialized via constructor." This creates a confusing two-path API. The `Init` method should either be removed from the interface or given a clear purpose. Until it's meaningful, it is dead interface weight that misrepresents how the class is actually used.

**`CESReader`: too many responsibilities.**

`/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/include/miem/ces_reader.hpp` conflates three jobs:
1. File I/O and lifecycle (open/close, NetCDF handle)
2. Format detection (CES-compliant vs descriptor-driven, `DetectFormat()`)
3. Variable name canonicalization (`CanonicalName()`, the reverse-rename logic in `ReadFlux`)

The reverse-rename loop in `ces_reader.cpp` lines 164-170 is particularly problematic: it iterates the full `descriptor_.species_rename` map for every species on every `ReadFlux` call. If a file has 50 species and 3000 cells, that is 50 map-scans per call. More importantly, it points to a design gap: `CanonicalName` converts file-var-name to canonical name, but `ReadFlux` needs the inverse. The correct solution is to pre-build a bidirectional name map during `Open`/`DiscoverSpecies` and store it, rather than re-deriving it on every read.

`CESReader` should ultimately split into a `NetCDFReader` (file handle + raw variable reads) and a `CESAdapter` (name canonicalization + format normalization). This is not urgent for v1 but will be needed before adding a second file format.

**`FluxConverter`: correctly minimal.**

A static utility class with two methods. Both are pure functions in practice (no state, no side effects). Consider whether it should be a free function in a `miem::physics` namespace rather than a class with only static methods. The class shell buys nothing here. Not a defect, but worth noting.

**`SpeciesMap`: correct but O(n) per `Apply` call.**

`Apply()` in `/Users/vweeks/NCAR/ACOM/CheMPAS/MIEM/src/species_map.cpp` lines 88-99 rebuilds `mech_idx` and `inv_idx` `std::map` objects from scratch on every invocation. For hourly timestep updates this cost is negligible, but it is worth caching these maps as pre-computed members, built once in the constructor or after `AddMapping`. ## 3. Memory Management

**RAII in C++ layer: good.**

The `test_error_default` test checks `error_is_success(err)` which only looks at `code`, but `error_message(err)` iterates `message(1:255)` looking for `c_null_char`. ```fortran
character(kind=c_char) :: category(64) = c_null_char
character(kind=c_char) :: message(256) = c_null_char
